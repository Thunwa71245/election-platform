# ระบบเลือกตั้งออนไลน์ภายในหน่วยงาน — ข้อกำหนด โครงสร้างระบบ และแผนพัฒนา

> สถานะเอกสาร: ฉบับร่างเพื่อทบทวนกับลูกค้า (8 ต.ค. 2569)
> ข้อใดที่ขึ้นต้นด้วย **[สมมติฐาน]** คือค่าที่ทีมตั้งไว้เพื่อให้ทำงานต่อได้ ยังไม่ใช่ข้อเท็จจริงที่ลูกค้ายืนยัน
> ข้อใดที่ขึ้นต้นด้วย **[ต้องยืนยัน]** ต้องได้คำตอบก่อนเริ่มระยะระบบจริง

## 0. สรุปสำหรับผู้บริหารโครงการ

1. **แยกงานเป็นสองระยะที่ส่งมอบต่างกันโดยสิ้นเชิง**
   - *ระยะต้นแบบ (Prototype)* — ให้ลูกค้าตรวจหน้าจอและขั้นตอน ใช้ข้อมูลสมมติ รหัสจำลอง และคะแนนจำลอง **ห้ามใช้รับคะแนนจริง** ทุกหน้าต้องมีแถบ “ต้นแบบ — ข้อมูลสมมติ ไม่ใช่การลงคะแนนจริง”
   - *ระยะระบบจริง (Production)* — มีฐานข้อมูล การยืนยันตัวตน การควบคุมสิทธิ์ฝั่งเซิร์ฟเวอร์ การบันทึกคะแนนแบบ transaction และการตรวจสอบย้อนหลัง
2. **ประเด็นที่ต้องตัดสินก่อนออกแบบฐานข้อมูลจริง** คือความหมายของ “หน่วยลงคะแนน” (หัวข้อ 2) เพราะกำหนดว่านับคะแนนและประกาศผลระดับไหน
3. **ความเสี่ยงสูงสุดด้านความลับของคะแนน** ไม่ได้อยู่ที่การแยกตาราง แต่อยู่ที่ *การให้ผู้ดูแลเห็นคะแนนสดพร้อมกับเห็นว่าใครใช้สิทธิ์แล้ว* ในหน่วยเล็ก ซึ่งจับคู่ได้ด้วยการสังเกตเวลา (หัวข้อ 7)
4. **วิธีเข้าสู่ระบบของสมาชิก** แนะนำแบบผสม: รหัส OTP อายุสั้นส่งไปช่องทางที่ลงทะเบียนไว้ + ช่องทางสำรองที่เจ้าหน้าที่ออกรหัสให้หลังตรวจบัตรต่อหน้า และควรถามก่อนว่าองค์กรมี SSO (เช่น Microsoft 365 / Google Workspace) หรือไม่ (หัวข้อ 5)
5. ระดับความลับที่ระบบนี้ให้ได้คือ **“ผู้ดูแลระบบผ่านหน้าแอปเชื่อมโยงสมาชิกกับคะแนนไม่ได้”** — ไม่ใช่การลงคะแนนลับต่อผู้ดูแลเซิร์ฟเวอร์/ฐานข้อมูล ต้องแจ้งลูกค้าตรง ๆ

## 2. การวิเคราะห์ความหมายของ “หน่วยลงคะแนน”

### 2.1 สองความหมายที่เป็นไปได้

| | **ก. เขตเลือกตั้ง (Contest)** | **ข. สถานที่ใช้สิทธิ์ (Polling place)** |
|---|---|---|
| ผู้สมัคร | ของหน่วยเอง | ชุดเดียวทั้งการเลือกตั้ง |
| ผู้มีสิทธิ์ | ของหน่วยเอง | แบ่งตามหน่วย แต่เลือกผู้สมัครชุดเดียวกัน |
| นับคะแนน | แยกหน่วย | รวมทุกหน่วย (ดูแยกหน่วยได้เพื่อสถิติ) |
| ประกาศผู้ชนะ | แยกหน่วย | รวมทั้งการเลือกตั้ง |
| ตัวอย่าง | สวัสดิการ: สนญ. เลือกกรรมการ สนญ., สาขาเลือกกรรมการสาขา | เลือกประธานคนเดียว แต่แบ่งรายชื่อตามสาขา |

### 2.2 ข้อสรุป
ข้อกำหนด “แต่ละหน่วยมีผู้สมัครของตนเอง” และ “หมายเลขผู้สมัครซ้ำกันได้ระหว่างหน่วย” ตรงกับ **ความหมาย ก. (เขตเลือกตั้ง)** ทีมจึงใช้ความหมายนี้เป็นค่าเริ่มต้น:

- **หน่วยลงคะแนน = หน่วยนับคะแนนและประกาศผล** มีผู้สมัคร ผู้มีสิทธิ์ กติกาจำนวนที่นั่งของตนเอง
- “สถานที่” เป็นเพียง *คุณสมบัติข้อความ* ของหน่วย ไม่ใช่หน่วยนับ
- ใน UI ยังใช้คำว่า “หน่วยลงคะแนน” ตามลูกค้า แต่ในโค้ดใช้ชื่อ `unit` (หรือ `contest`) และใส่คำอธิบายในหน้าสร้างหน่วยว่า “ผลคะแนนและผู้ชนะจะนับแยกตามหน่วย”

**[ต้องยืนยัน]** หากลูกค้าต้องการความหมาย ข. ด้วย (ผู้สมัครชุดเดียว นับรวม) ให้ถือเป็นข้อกำหนดเพิ่ม — โมเดลรองรับได้โดยเพิ่ม “กลุ่มนับรวม” ภายหลัง แต่ **ไม่ทำในรอบนี้** เพื่อไม่ให้กติกาการนับกำกวม

### 2.3 ค่าเริ่มต้นของต้นแบบ vs กติกาที่ต้องยืนยันก่อนใช้จริง

| ประเด็น | ค่าเริ่มต้นในต้นแบบ | ต้องยืนยันก่อนระบบจริง |
|---|---|---|
| สมาชิกมีสิทธิ์หลายหน่วยใน *การเลือกตั้งเดียวกัน* | **ไม่ได้** — ระบบเตือน/ปฏิเสธตอนเพิ่มหรือนำเข้า (เปิดเป็นค่าตั้งค่าต่อการเลือกตั้งได้) | ใช่/ไม่ใช่ |
| สมาชิกมีสิทธิ์หลาย *การเลือกตั้ง* | ได้ ตรวจแยกรายการ | — |
| ระดับประกาศผล | แยกหน่วย | ยืนยันตามข้อ 2.2 |
| เวลาเปิด–ปิด | กำหนดที่การเลือกตั้ง; หน่วยกำหนดทับได้ (ค่าที่ใช้จริง = ค่าหน่วย ?? ค่าการเลือกตั้ง) | หน่วยกำหนดทับได้หรือไม่ |
| จำนวนที่นั่ง (`seats`) | 1 | ต่อหน่วยหรือต่อการเลือกตั้ง |
| จำนวนที่เลือกได้ | ต่ำสุด 1 สูงสุด 1 (ตั้งค่าได้ `min_selections` ≤ `max_selections` ≤ `seats`) | ต้องเลือกครบหรือเลือกน้อยกว่าได้ |
| ไม่ประสงค์ลงคะแนน | เปิด; เลือกพร้อมผู้สมัครไม่ได้ | เปิด/ปิดต่อการเลือกตั้ง |
| หมวด/ตำแหน่ง | 1 ตำแหน่งต่อการเลือกตั้ง | ต้องการหลายตำแหน่งในบัตรเดียวหรือไม่ (ถ้าใช่ = งานเพิ่มขนาดใหญ่) |
| กฎผู้ชนะ | คะแนนสูงสุด `seats` อันดับแรก; เสมอที่ลำดับตัด → ไม่ประกาศอัตโนมัติ | วิธีตัดสินเสมอ, ผู้สมัครคนเดียวต้องได้คะแนนเกิน “ไม่ประสงค์” หรือเกณฑ์ขั้นต่ำหรือไม่, องค์ประชุม/turnout ขั้นต่ำ |
| สมาชิกเห็นผลหลังประกาศ | แสดงผู้ชนะที่ประกาศแล้วในหน้าสมาชิก (ไม่แสดงคะแนนรายคน) | ยืนยันว่าจะให้เห็นอะไร |

## 3. ขอบเขตและบทบาท

### 3.1 บทบาทผู้ใช้ (ระบบจริง)
| บทบาท | ทำได้ |
|---|---|
| ผู้ดูแลสูงสุด (super_admin) | จัดการผู้ดูแล, กำหนดสิทธิ์, ทุกอย่าง |
| ผู้ดูแลการเลือกตั้ง (election_admin) — ผูกกับการเลือกตั้งที่ได้รับมอบ | สร้าง/แก้การเลือกตั้ง หน่วย ผู้สมัคร ผู้มีสิทธิ์ ดูสถิติการใช้สิทธิ์ |
| ผู้ดูคะแนนระหว่างเลือกตั้ง (live_results_viewer) | ดูคะแนนสด **ต้องได้รับมอบแยก** |
| ผู้รับรองผล (results_certifier) | ตรวจผลหลังปิดหีบ และกดประกาศ |
| เจ้าหน้าที่ช่วยเหลือ (helpdesk) | ค้นหาสมาชิก, ออกรหัสสำรองหลังตรวจตัวตน (ไม่เห็นคะแนน) |
| สมาชิก (member) | ลงคะแนนในรายการที่มีสิทธิ์ |

ทุกสิทธิ์ของผู้ดูแล (ยกเว้น super_admin) ผูกกับขอบเขตการเลือกตั้ง ต้นแบบใช้บัญชีตัวอย่างบทบาทละหนึ่งบัญชี

### 3.2 นอกขอบเขตรอบนี้
- การลงคะแนนแบบเข้ารหัสที่พิสูจน์ได้ (end-to-end verifiable, mixnet, blind signature)
- หลายตำแหน่งในบัตรเดียว, การลงคะแนนแบบจัดอันดับ
- แอปมือถือ native (ใช้เว็บที่รองรับมือถือ)

## 4. ข้อกำหนดเชิงหน้าที่ (สรุปพร้อมการตัดสินใจ)

### 4.1 วงจรสถานะ
```
การเลือกตั้ง:  ฉบับร่าง → เผยแพร่แล้ว → (คำนวณจากเวลาเซิร์ฟเวอร์) ยังไม่เปิด / กำลังเปิด / ปิดแล้ว → ประกาศผลแล้ว
                          ↘ ยกเลิก
หน่วย:         ใช้งาน / ยกเลิก  (สถานะเวลาคำนวณจากเวลาที่มีผลของหน่วย)
ผลต่อหน่วย:    ยังไม่ปิด → รอตรวจสอบ → ต้องตัดสิน (เสมอ/ผู้สมัครไม่พอ/ไม่มีผู้ลงคะแนน) → ประกาศแล้ว
```
- “ยังไม่เปิด/กำลังเปิด/ปิดแล้ว” **คำนวณจากเวลาเซิร์ฟเวอร์ทุกครั้ง** ไม่เก็บเป็น flag ที่ต้องมีคนกด และไม่เชื่อเวลาจากเครื่องผู้ใช้
- ปิดหีบก่อนเวลา (กรณีฉุกเฉิน) ทำได้โดยผู้ดูแลสูงสุด พร้อมเหตุผล บันทึก audit

### 4.2 เวลา
- เก็บเป็น `timestamptz` (UTC) ในฐานข้อมูล แสดงผลเป็นเวลาไทย `Asia/Bangkok` ปี พ.ศ. เช่น “15 ต.ค. 2569 08:30 น.”
- ฟอร์มรับเวลาเป็นเวลาไทยแล้วแปลงเป็น UTC ฝั่งเซิร์ฟเวอร์; ตรวจ `close_at > open_at` ทั้งฝั่ง client และ server
- เซิร์ฟเวอร์ต้อง sync NTP; หน้าสมาชิก/ผู้ดูแลแสดงเวลาที่มาจาก API ไม่ใช่ `new Date()` ฝั่งเครื่อง

### 4.3 ข้อจำกัดการแก้ไขตามสถานะ
| ข้อมูล | ฉบับร่าง | เผยแพร่แล้ว ยังไม่เปิด | กำลังเปิด | ปิดแล้ว/ประกาศแล้ว |
|---|---|---|---|---|
| ชื่อ/รายละเอียด/สถานที่ | แก้ได้ | แก้ได้ (audit) | แก้ข้อความแสดงผลได้ (audit) | อ่านอย่างเดียว |
| กติกา (ที่นั่ง, จำนวนเลือก, ไม่ประสงค์, กฎผู้ชนะ) | แก้ได้ | แก้ได้ + เตือน | **ล็อก** | ล็อก |
| ผู้สมัคร | แก้ได้ | แก้ได้ + เตือน | **ล็อก** (แก้คำผิดในประวัติได้โดย super_admin + audit, เปลี่ยนหมายเลข/เพิ่ม/ลบไม่ได้) | ล็อก |
| ผู้มีสิทธิ์ | แก้ได้ | แก้ได้ | เพิ่มได้ (audit + เหตุผล); ลบได้เฉพาะคนที่ยังไม่ใช้สิทธิ์ (audit); ห้ามแก้สถานะการใช้สิทธิ์ด้วยมือ | ล็อก |
| เวลาเปิด | แก้ได้ | แก้ได้ | ล็อก | ล็อก |
| เวลาปิด | แก้ได้ | แก้ได้ | ขยายได้ (audit + เหตุผล), ย่นได้ไม่น้อยกว่าเวลาปัจจุบัน | ล็อก |
| ยกเลิกหน่วย | ได้ | ได้ | ได้เฉพาะ super_admin (ต้องกำหนดว่าคะแนนที่มีแล้วจะทำอย่างไร — **[ต้องยืนยัน]**) | ไม่ได้ |

### 4.4 ลิงก์ใช้สิทธิ์และ QR
- รูปแบบ: `/user/u/{unitPublicId}` โดย `unitPublicId` เป็นค่าสุ่มที่เดาไม่ได้ (เช่น 22 ตัวอักษร base62) **ไม่ใช่** id ลำดับ และไม่ใช้ชื่อหน่วย/ปี — หน่วยของการเลือกตั้งปีอื่นจึงเป็นคนละ id เสมอ ไม่ปะปนกัน
- ลิงก์เป็นแค่ “ทางเข้า” ไม่ใช่หลักฐานสิทธิ์; เซิร์ฟเวอร์ตรวจสิทธิ์ทุกครั้งทั้งตอนอ่านและส่งคะแนน
- หลังบันทึกหน่วย: แสดงลิงก์, ปุ่มคัดลอก, QR (สร้างฝั่ง client จากลิงก์ ดาวน์โหลด PNG ได้), ปุ่ม “ดูตัวอย่างหน้าสมาชิก”
- พฤติกรรมเมื่อเปิดลิงก์ตามสถานะ:

| สถานะ | ผู้เปิดลิงก์ที่มีสิทธิ์ | ผู้ไม่มีสิทธิ์ |
|---|---|---|
| id ไม่มีจริง / การเลือกตั้งยังเป็นฉบับร่าง | “ไม่พบหน่วยลงคะแนน หรือยังไม่พร้อมใช้งาน” (ข้อความเดียวกัน ไม่บอกว่ามีอยู่) | เหมือนกัน |
| เผยแพร่แล้ว ยังไม่เปิด | ข้อมูลหน่วย ผู้สมัคร เวลาเปิด “ยังไม่เปิดหีบ” ปุ่มลงคะแนนปิดอยู่ | “คุณไม่มีสิทธิ์ลงคะแนนในหน่วยนี้” + ปุ่ม “ดูหน่วยที่ฉันมีสิทธิ์” |
| กำลังเปิด ยังไม่ใช้สิทธิ์ | หน้าลงคะแนน | เหมือนข้างบน |
| ใช้สิทธิ์แล้ว | แถบเขียว “ใช้สิทธิ์แล้ว” ไม่มีปุ่มลงคะแนน | เหมือนข้างบน |
| ปิดแล้ว / ประกาศแล้ว | “ปิดหีบแล้ว” (+ ผู้ชนะถ้าประกาศและลูกค้าอนุญาต) | เหมือนข้างบน |
| หน่วยถูกยกเลิก | “หน่วยลงคะแนนนี้ถูกยกเลิก” | “คุณไม่มีสิทธิ์ลงคะแนนในหน่วยนี้” |

- “ยังไม่พร้อมใช้สิทธิ์” จนกว่า: การเลือกตั้ง *เผยแพร่แล้ว* + หน่วย *ใช้งาน* + มีผู้สมัครอย่างน้อย 1 คน + มีผู้มีสิทธิ์อย่างน้อย 1 คน (ระบบตรวจ checklist ก่อนให้กดเผยแพร่)

### 4.5 โหมดดูตัวอย่าง (Preview)
- อยู่ใต้ `/admin/.../preview` ใช้ session ผู้ดูแล ไม่ใช่ session สมาชิก
- มีลายน้ำ “โหมดดูตัวอย่าง — ไม่มีการบันทึกคะแนน” ทุกหน้าจอ
- ปุ่มยืนยันในป๊อปอัปแค่ปิดป๊อปอัปและแสดง “(ตัวอย่าง) ระบบจะบันทึกคะแนนที่ขั้นตอนนี้”
- เซิร์ฟเวอร์ **ปฏิเสธ** คำขอลงคะแนนที่ไม่ได้มาจาก session สมาชิกเสมอ (ไม่พึ่งการซ่อนปุ่ม)

### 4.6 ผู้สมัคร
- `candidate.id` (รหัสภายใน UUID) แยกจาก `number` (หมายเลขที่แสดง)
- unique(`unit_id`, `number`); หมายเลขซ้ำข้ามหน่วยได้
- รูป: jpg/png/webp ≤ 2 MB, ครอปเป็นสัดส่วนเดียวกัน (เช่น 3:4) ฝั่งเซิร์ฟเวอร์, ตัด EXIF
- ผู้สมัครเป็นข้อมูล *ของหน่วยนั้น* ไม่อ้างอิงโปรไฟล์บุคคลกลาง → แก้ข้อมูลครั้งใหม่ไม่กระทบประวัติครั้งเก่า (ถ้าจะ “ใช้ข้อมูลเดิม” ให้เป็นการคัดลอก)

### 4.7 ผู้มีสิทธิ์และการนำเข้า Excel
- ทะเบียนสมาชิก (`member`) เป็นข้อมูลกลาง; สิทธิ์ (`eligibility`) ผูก member × unit
- `eligibility` เก็บ snapshot ชื่อ–สังกัด ณ วันที่นำเข้า → ประวัติไม่เปลี่ยนเมื่อแก้ทะเบียนภายหลัง
- `member_code` เป็น **ข้อความ** ทุกชั้น (DB `text`, parse Excel เป็น string, template ตั้งรูปแบบเซลล์เป็น Text `@`)
- ขั้นตอน 8 ขั้นตามที่ลูกค้ากำหนด; ตรวจ: คอลัมน์ครบ, ค่าว่าง, รหัสซ้ำในไฟล์, ซ้ำกับหน่วยนี้, มีสิทธิ์หน่วยอื่นในการเลือกตั้งเดียวกัน (ตามกติกา 2.3), รูปแบบอีเมล/เบอร์, เซลล์รหัสที่เป็นตัวเลข (เตือนว่าเลข 0 อาจหายไปแล้ว)
- **นโยบายเมื่อพบสมาชิกเดิม (ค่าเริ่มต้น)**:
  - มีสิทธิ์ในหน่วยนี้อยู่แล้ว → **ข้าม** และรายงาน (ไม่แตะสถานะใช้สิทธิ์เด็ดขาด)
  - มีในทะเบียนแต่ชื่อ/สังกัดในไฟล์ต่าง → แสดงเป็น “ต้องตรวจสอบ” ให้ผู้ดูแลเลือกต่อแถว: ใช้ข้อมูลทะเบียนเดิม / อัปเดตทะเบียน
  - ช่องทางติดต่อในไฟล์ต่างจากทะเบียน → **ไม่อัปเดตอัตโนมัติ** (เพราะคือช่องทางรับรหัส) ต้องใช้สิทธิ์ผู้ดูแลแยก + audit
  - การนำเข้าไม่ลบสิทธิ์ใคร
- การนำเข้าเป็น transaction เดียว (สำเร็จทั้งชุดตามรายการที่ยืนยัน หรือไม่บันทึกเลย); จำกัดขนาดไฟล์ (เช่น 5 MB / 20,000 แถว **[สมมติฐาน]**)
- ส่งออกรายงานข้อผิดพลาด: ป้องกัน CSV/Excel formula injection (ขึ้นต้น `= + - @` ให้ใส่ `'`)

### 4.8 ผลคะแนนและประกาศผล
- คะแนนสด: polling ทุก 30 วินาที **[สมมติฐาน]** (ง่ายกว่า WebSocket สำหรับทีมเล็ก) แสดง “อัปเดตล่าสุด”, สถานะการเชื่อมต่อ (เชื่อมต่อ/ขาดการเชื่อมต่อ ลองใหม่อัตโนมัติ)
- ระหว่างเปิดหีบ ใช้หัวข้อ “คะแนนระหว่างการเลือกตั้ง” และไม่แสดงคำว่า “ผู้ชนะ”
- หลังปิดหีบ: ระบบคำนวณผลเสนอ → ผู้รับรองผลตรวจ → กดประกาศ → ระบบเก็บ snapshot ผลที่ไม่เปลี่ยนแปลง (`result_certification`) พร้อมผู้ประกาศและเวลา
- กรณีพิเศษที่ไม่ประกาศอัตโนมัติ: เสมอที่ลำดับตัด, ไม่มีผู้ลงคะแนน, ผู้สมัครน้อยกว่าที่นั่ง, ผู้สมัครคนเดียว (รอกฎ), กติกายังเป็น “ยังไม่กำหนด” → สถานะ “ต้องตัดสิน” ผู้รับรองต้องบันทึกการตัดสินพร้อมเหตุผล
- ข้อมูลที่แสดง: คะแนนผู้สมัคร, ไม่ประสงค์ลงคะแนน, จำนวนผู้ใช้สิทธิ์, จำนวนผู้มีสิทธิ์, % ใช้สิทธิ์; ตรวจสอบความสอดคล้อง: จำนวนบัตร = จำนวนผู้ใช้สิทธิ์ (ถ้าไม่ตรง แสดงคำเตือนแดง)

### 4.9 ประวัติย้อนหลัง
- แสดงต่อการเลือกตั้ง → หน่วย: ผู้จัด, สถานที่, เวลา, ผู้มีสิทธิ์, ผู้ใช้สิทธิ์, ผลคะแนนรวม, ผู้ชนะที่ประกาศ, สถานะประกาศ
- ใช้ข้อมูลจาก snapshot/ข้อมูลของการเลือกตั้งนั้นเท่านั้น (ผู้สมัครต่อหน่วย, snapshot ใน eligibility, snapshot ชื่อหน่วยงานผู้จัดใน election)

### 4.10 ส่วนสมาชิก
- `/user/login` → รหัสสมาชิก + รหัสเข้าใช้ + ปุ่มขอรหัส; รองรับสถานะ: กำลังดำเนินการ, ขอสำเร็จ (แสดงช่องทางแบบปิดบัง), รหัสผิด, หมดอายุ, ถูกล็อกชั่วคราว
- เปิดลิงก์หน่วยตอนยังไม่เข้าสู่ระบบ → เข้าสู่ระบบ → กลับหน่วยเดิม (`next` ต้องเป็น path ภายใน `/user/...` เท่านั้น กัน open redirect)
- `/user` หน้ารายการที่มีสิทธิ์: ชื่อ สังกัด และการ์ดต่อสิทธิ์ (การเลือกตั้ง, หน่วย, สถานที่, เวลา, กติกา, สถานะของสมาชิกคนนั้นในรายการนั้น, ปุ่มลงคะแนน)
- หน้าลงคะแนน: การ์ดรูปขนาดเท่ากัน, หมายเลข, ชื่อ, ปุ่มดูประวัติ/นโยบาย (modal), สถานะเลือกชัด (กรอบ + เครื่องหมายถูก + ไม่พึ่งสีอย่างเดียว), กติกา “เลือกได้ N คน”, ตัวเลือกไม่ประสงค์ (exclusive)
  - เลือก 1 คน: แตะการ์ด → เปิดป๊อปอัปยืนยันทันที
  - เลือกหลายคน: แตะเพื่อเลือก/ยกเลิก, ปุ่ม “ตรวจทานและยืนยัน” เปิดได้เมื่อเลือกครบตามกติกา → ป๊อปอัปแสดงทุกคน
- ป๊อปอัป: รูป หมายเลข ชื่อ, “คุณต้องการยืนยันลงคะแนนให้ผู้สมัครคนนี้ใช่หรือไม่?”, “เมื่อส่งคะแนนสำเร็จแล้วจะเปลี่ยนไม่ได้”, ปุ่ม “กลับไปเลือกใหม่” / “ยืนยันลงคะแนน”; กรณีไม่ประสงค์: “คุณต้องการยืนยันไม่ประสงค์ลงคะแนนใช่หรือไม่?”
- ส่งคะแนน: ปุ่มเป็น loading + disable, ปิดป๊อปอัปไม่ได้ระหว่างส่ง; สำเร็จ → กลับ `/user` + แถบเขียว “ใช้สิทธิ์แล้ว” ที่รายการนั้น + toast “บันทึกคะแนนเรียบร้อยแล้ว” (ไม่ระบุผู้สมัคร)
- ไม่มีการยืนยันตัวตนซ้ำก่อนลงคะแนน (login ครั้งเดียวพอ ภายในอายุ session)

### 4.11 การจัดการผลการส่งที่ไม่แน่นอน
| ผลที่ได้ | ความหมาย | UI |
|---|---|---|
| 2xx `recorded` | บันทึกแล้ว | กลับหน้ารายการ แถบเขียว |
| 409 `already_voted` | สิทธิ์นี้ใช้ไปแล้ว (อาจจากแท็บอื่น) | แถบเขียว “ใช้สิทธิ์แล้ว” |
| 4xx ที่ระบุว่าไม่ได้บันทึก (หีบปิด, ตัวเลือกไม่ถูกต้อง, ไม่มีสิทธิ์, session หมด) | **ไม่สำเร็จแน่นอน** | แจ้งเหตุผล, ให้ทำต่อตามกรณี |
| timeout / เครือข่ายหลุด / 5xx | **ยังไม่ทราบผล** | “กำลังตรวจสอบสถานะการลงคะแนน…” → เรียก `GET` สถานะสิทธิ์ ซ้ำแบบ backoff → ถ้าใช้สิทธิ์แล้ว = สำเร็จ; ถ้ายังไม่ใช้ = ให้กดส่งใหม่ **ด้วย idempotency key เดิม**; ถ้าตรวจไม่ได้ = “ยังไม่ทราบผล กรุณาอย่าปิดหน้านี้ / ลองตรวจสถานะอีกครั้ง” |

## 5. การยืนยันตัวตนของสมาชิก

### 5.1 เปรียบเทียบ
| เกณฑ์ | A. รหัสเฉพาะบุคคลที่ผู้ดูแลแจก | B. OTP อายุสั้นส่งไปช่องทางที่ลงทะเบียน | C. SSO ขององค์กร |
|---|---|---|---|
| ต้องมีอีเมล/เบอร์ในระบบ | ไม่ | ต้อง | ต้องมีบัญชีองค์กร |
| ค่าใช้จ่าย | งานคน (พิมพ์/แจก) | SMS มีค่าใช้จ่ายต่อข้อความ; อีเมลถูก | ต่ำ ถ้ามีอยู่แล้ว |
| ความเสี่ยงหลัก | ผู้ออกรหัสรู้รหัส → **สวมสิทธิ์ได้**; รหัสหลุดระหว่างแจก | ช่องทางติดต่อผิด/ถูกยึด, ส่งไม่ถึง | ขึ้นกับความปลอดภัยของ IdP |
| ภาระทีมพัฒนา | ต่ำ | กลาง (ผู้ให้บริการส่งข้อความ, rate limit) | กลาง (OIDC/SAML) |
| ประสบการณ์ผู้ใช้ | ต้องเก็บรหัส | ขอเมื่อต้องการ | ดีที่สุด |

### 5.2 ข้อเสนอ
1. **ถามก่อน: องค์กรมี SSO ที่สมาชิกทุกคนมีบัญชีหรือไม่** ถ้ามี → ใช้ C เป็นหลัก
2. ถ้าไม่มี → **B เป็นหลัก** (อีเมลเป็นค่าเริ่มต้นเพราะต้นทุนต่ำ, SMS/LINE เป็นทางเลือก **[ต้องยืนยัน]**) + **A แบบควบคุม เป็นช่องทางสำรอง** สำหรับคนไม่มีช่องทางติดต่อ:
   - เจ้าหน้าที่ helpdesk ตรวจบัตรพนักงาน/บัตรสมาชิก *ต่อหน้าหรือวิดีโอคอล* แล้วกดออกรหัส
   - รหัสแสดงครั้งเดียว ระบบเก็บเฉพาะ hash, ผู้ออกเรียกดูซ้ำไม่ได้, ออกใหม่ = รหัสเก่าถูกยกเลิก, บันทึก audit (ใครออกให้ใคร เวลาใด)
   - **ความเสี่ยงที่เหลือ**: เจ้าหน้าที่ที่ออกรหัสสามารถสวมสิทธิ์ได้ในทางทฤษฎี — ลดด้วย audit, รายงานรหัสสำรองที่ออกต่อการเลือกตั้งให้กรรมการตรวจ, และแจ้งสมาชิกในหน้ารายการว่า “สิทธิ์นี้ใช้แล้วเมื่อ…(วันที่)” ถ้ามีคนอ้างว่าไม่ได้ลง → มีกระบวนการร้องเรียน **[ต้องยืนยัน]**
3. การรู้แค่รหัสสมาชิก **ไม่พอ** จะได้รหัส เพราะรหัสส่งไปช่องทางที่ลงทะเบียนเท่านั้น; ผู้ขอเปลี่ยนช่องทางเองไม่ได้ (เปลี่ยนได้โดยผู้ดูแลที่มีสิทธิ์ + audit + แจ้งเตือนไปช่องทางเดิม)

### 5.3 พารามิเตอร์ (ค่าเริ่มต้น **[สมมติฐาน]**)
| รายการ | ค่า |
|---|---|
| รูปแบบ OTP | ตัวเลข 6 หลัก, สร้างด้วย CSPRNG, เก็บ hash |
| อายุ OTP | 5 นาที, ใช้ครั้งเดียว |
| รหัสสำรองจาก helpdesk | 8–10 ตัวอักษร (ตัดตัวสับสน 0/O/1/l), อายุถึงเวลาปิดหีบของรายการที่เกี่ยวข้อง หรือ 24 ชม. แล้วแต่อย่างใดก่อน |
| ขอรหัสใหม่ | รหัสเก่ายกเลิกทันที; cooldown 60 วินาที; ≤ 5 ครั้ง/ชม./สมาชิก; ≤ 20 ครั้ง/ชม./IP |

| Session | cookie `HttpOnly; Secure; SameSite=Lax`, idle 30 นาที, สูงสุด 8 ชม., แยก cookie สมาชิกกับผู้ดูแล |

หมายเหตุความเสี่ยง: การแสดงช่องทางแบบปิดบังยืนยันโดยอ้อมว่ารหัสสมาชิกนั้นมีอยู่ (account enumeration) — ลูกค้าต้องการฟีเจอร์นี้ จึงชดเชยด้วย rate limit และไม่แสดงช่องทางเต็ม

### 5.4 ผู้ดูแล
- `/admin/login` แยก ไม่มีลิงก์จากหน้าสมาชิก; รหัสผ่าน (argon2id/bcrypt) + **MFA (TOTP) แนะนำในระบบจริง** **[ต้องยืนยัน]** หรือ SSO
- ทุกการกระทำสำคัญบันทึก `admin_audit_log`

### 5.5 ต้นแบบ
- ปุ่ม “ขอรหัส” แสดง “(จำลอง) ส่งรหัสไปที่ s****@example.com แล้ว” และแสดงรหัสจำลองในกล่องสำหรับผู้ทดสอบ; ไม่ส่งข้อความจริง ไม่มี API key ผู้ให้บริการใด ๆ ใน repo
- บัญชีตัวอย่าง: สมาชิกที่มีสิทธิ์ 1 รายการ, 2 รายการ (คนละการเลือกตั้ง), ใช้สิทธิ์แล้ว, ไม่มีสิทธิ์, ไม่มีช่องทางติดต่อ; ผู้ดูแลแต่ละบทบาท

### 6.1 เทคโนโลยี **[สมมติฐาน — ยังไม่ยืนยัน]**
ถ้าต้นแบบเดิมใช้ stack ใดอยู่และใช้ต่อได้ ให้ใช้ต่อ หากเริ่มเลือกใหม่ แนะนำสำหรับทีมเล็ก:
- **TypeScript full-stack** หนึ่งแอป (เช่น Next.js หรือ React + Node API) — UI และ API อยู่ใน repo เดียว deploy ง่าย
- **PostgreSQL** (transaction, row lock, `timestamptz`, unique constraint ที่จำเป็นต่อการกันลงซ้ำ)
- ORM/Query builder ที่มี migration (Prisma หรือ Drizzle)
- ตรวจ input ด้วย schema (เช่น Zod) ใช้ร่วม client/server
- ทดสอบ: unit (Vitest/Jest), integration กับ Postgres จริง, E2E (Playwright)
- โฮสติ้ง/งบ/ผู้ใช้พร้อมกัน **ยังไม่ทราบ** — ออกแบบให้รันได้บน VM เดียว + Postgres managed; ตัวเลขโหลดต้องได้จากลูกค้า (หัวข้อ 9)

### 6.4 การบันทึกคะแนน (ลำดับใน transaction เดียว)
```
POST /api/user/units/{publicId}/ballot
body: { submissionKey: uuid, candidateIds: [...], abstain: bool }

BEGIN
 1. หา unit + election จาก publicId; ตรวจ published, unit active,
    now() (เวลา DB) อยู่ใน [open_at, close_at)            → ไม่ผ่าน = 4xx ไม่บันทึก
 2. SELECT eligibility WHERE unit_id=? AND member_id=session.member FOR UPDATE
    - ไม่พบ → 403
    - has_voted AND submission_key = body.submissionKey → 200 recorded (idempotent)
    - has_voted → 409 already_voted
 3. ตรวจตัวเลือก: candidate อยู่ใน unit นี้, ไม่ซ้ำ, จำนวนอยู่ใน [min,max],
    abstain ต้องไม่มี candidate และ allow_abstain = true  → ไม่ผ่าน = 422
 4. INSERT ballot (+ ballot_choice)
 5. UPDATE eligibility SET has_voted=true, submission_key=? WHERE id=? AND has_voted=false
    (ตรวจ rowcount = 1 เป็นชั้นป้องกันที่สอง)
COMMIT
→ 200 { status: "recorded" }   (ไม่ส่งตัวเลือกกลับ)
```
- หลายแท็บ/หลายอุปกรณ์ส่งพร้อมกัน: `FOR UPDATE` ทำให้คำขอที่สองรอ แล้วเห็น `has_voted=true` → 409 หรือ 200 (ถ้า key เดียวกัน)
- `submission_key` สร้างฝั่ง client ตอนเปิดป๊อปอัปยืนยัน และใช้ซ้ำทุกครั้งที่ลองส่งใหม่ของการยืนยันครั้งนั้น; เก็บใน eligibility (ฝั่งตัวตน) **ไม่เก็บใน ballot**
- `GET /api/user/entitlements` คืนสถานะต่อรายการ ใช้ทั้งหน้ารายการและการกู้สถานะ

## 7. ความลับและความถูกต้องของคะแนน — การวิเคราะห์ตรงไปตรงมา

### 7.1 สิ่งที่สถาปัตยกรรมนี้ป้องกันได้
| ผู้โจมตี/ผู้สังเกต | ป้องกันได้? | เพราะ |
|---|---|---|
| สมาชิกคนอื่น | ได้ | ไม่มี API ใดคืนตัวเลือกของคนอื่น |
| ผู้ดูแลผ่านหน้าแอป (ทุกบทบาท) | **ได้เป็นส่วนใหญ่** | ไม่มีหน้า/รายงาน/ส่งออกที่จับคู่สมาชิก–ตัวเลือก; ballot ไม่มี member_id/เวลา — *ยกเว้นช่องโหว่จากคะแนนสดในหน่วยเล็ก (7.2) และกรณีผลเอกฉันท์* |
| ผู้ดูแลที่เข้าถึงฐานข้อมูลโดยตรง | **บางส่วน** | ไม่มีคอลัมน์เชื่อมโยง แต่ลำดับการเขียนทางกายภาพ (ctid/WAL), transaction log, backup ที่ถ่ายระหว่างวัน อาจอนุมานลำดับได้เมื่อประกอบกับข้อมูลอื่น |
| ผู้ดูแลโฮสต์/เซิร์ฟเวอร์ (เห็น log, memory, เครือข่าย) | **ไม่ได้** | เขาเห็นคำขอที่มาพร้อม session ของสมาชิกและตัวเลือกในเวลาเดียวกัน — การป้องกันระดับนี้ต้องใช้คริปโตแบบ blind signature/mixnet ซึ่งอยู่นอกขอบเขต |

ข้อสรุปที่ต้องแจ้งลูกค้า: ระบบนี้เป็น **“การลงคะแนนที่ผู้ดูแลการเลือกตั้งมองไม่เห็นตัวเลือกรายบุคคล”** โดยอาศัยการควบคุมการเข้าถึงโครงสร้างพื้นฐาน (ผู้ดูแลเซิร์ฟเวอร์ต้องเป็นบุคคลที่เชื่อถือได้และแยกจากผู้ดูแลการเลือกตั้ง) ไม่ใช่การลงคะแนนลับที่พิสูจน์ได้ทางคณิตศาสตร์

### 7.2 คะแนนสดกับความลับในหน่วยเล็ก
ปัญหา: ผู้ดูแลเห็น (1) รายชื่อว่าใครใช้สิทธิ์แล้ว และ (2) คะแนนสด → ถ้าระหว่างรีเฟรชสองครั้งมีคนใช้สิทธิ์เพิ่มคนเดียว และคะแนนผู้สมัคร X เพิ่ม 1 → รู้ทันทีว่าคนนั้นเลือก X ในหน่วย 10 คนทำได้ง่ายมาก ในหน่วยใหญ่ช่วงที่คนน้อย (เช้ามืด) ก็ทำได้

ข้อเสนอ (ไม่ตัดฟีเจอร์ แต่จำกัด) — ค่าเริ่มต้น **[สมมติฐาน]** ให้ลูกค้ายืนยัน:
1. **แยกสิทธิ์**: ผู้มีบทบาท `live_results_viewer` ไม่เห็นสถานะใช้สิทธิ์ *รายบุคคล* ระหว่างเปิดหีบ (เห็นแค่จำนวนรวม) — ถ้าคนเดียวต้องมีทั้งสองบทบาท ต้องใช้ข้อ 2–3
2. **คะแนนสดเป็น snapshot เป็นช่วง** (เช่น ทุก 10 นาที) ไม่ใช่ทุกคะแนน และ **แสดงเฉพาะเมื่อมีบัตรใหม่ ≥ k ใบ (เช่น k=5) นับจาก snapshot ก่อน** มิฉะนั้นค้างค่าเดิม
3. **เกณฑ์ขั้นต่ำต่อหน่วย**: ถ้าผู้ใช้สิทธิ์ < 10 คน **[สมมติฐาน]** แสดงเฉพาะจำนวนผู้ใช้สิทธิ์ ไม่แสดงคะแนนแยกผู้สมัคร จนกว่าจะปิดหีบ
4. หน้ารายชื่อผู้มีสิทธิ์แสดงสถานะ “ใช้แล้ว/ยังไม่ใช้” **ไม่แสดงเวลา**
5. ตอนสร้างหน่วยที่มีผู้มีสิทธิ์น้อยกว่าเกณฑ์ แสดงคำเตือนเรื่องความลับ
6. บันทึก audit ทุกครั้งที่มีผู้เปิดดูคะแนนสด
7. ยอมรับข้อจำกัดโดยธรรมชาติ: ผลเอกฉันท์ หรือหน่วยที่ผู้สมัครได้ 0 คะแนน เปิดเผยตัวเลือกของทุกคนหลังปิดหีบอยู่แล้ว — เป็นเรื่องกติกาไม่ใช่ซอฟต์แวร์

### 7.3 ข้อมูลรั่วผ่านช่องทางข้างเคียง
| ช่องทาง | มาตรการ |
|---|---|
| Ballot | UUID v4 สุ่ม (ห้าม UUIDv7/ULID/serial ที่เรียงตามเวลา), ไม่มี created_at; ถ้าต้องการลดการอนุมานจากลำดับกายภาพ ใช้ตารางนับ (`tally`) แทนการเก็บบัตรรายใบ — **trade-off**: ตรวจนับซ้ำรายใบไม่ได้ → เสนอเก็บบัตรรายใบ (ตรวจสอบได้) เป็นค่าเริ่มต้น และให้ลูกค้าเลือก |
| eligibility | ไม่เก็บ `voted_at` ละเอียด (ถ้าลูกค้าต้องการกราฟการใช้สิทธิ์ตามเวลา ใช้ตัวนับรวมรายชั่วโมงแยกตาราง) |
| Application log | ห้ามบันทึก body ของ endpoint ลงคะแนน, ห้ามบันทึก candidateIds; log ได้แค่ `unit_id`, ผลลัพธ์ (recorded/409/422) |
| DB log | ปิด statement logging ที่มีพารามิเตอร์ (`log_statement`, slow-query log พร้อมค่า) สำหรับ production |
| Reverse proxy / access log | ตัวเลือกไม่อยู่ใน URL/query string (ใช้ POST body เท่านั้น); กำหนดอายุ log สั้น **[ต้องยืนยัน นโยบายเก็บ log]** |
| Error tracking (เช่น Sentry) | scrub request body และ state ของหน้าลงคะแนน |
| Analytics | **ไม่ติด analytics/third-party script ใด ๆ ในหน้า `/user`** |
| Client | ไม่เก็บตัวเลือกใน localStorage/sessionStorage/URL; ข้อความสำเร็จไม่ระบุผู้สมัคร; ไม่มี “ใบยืนยันการลงคะแนน” ที่ระบุตัวเลือก (กันการซื้อเสียง/บังคับ) |
| Backup | เข้ารหัส, จำกัดผู้เข้าถึง, หลีกเลี่ยง snapshot ถี่ระหว่างเปิดหีบถ้าไม่จำเป็น (ต้องชั่งกับการกู้คืน) |
| Response timing/size | การตอบกลับ recorded มีขนาดเท่ากันทุกตัวเลือก |

### 7.4 ความถูกต้อง
- กันใช้สิทธิ์ซ้ำ: unique(unit_id, member_id) + row lock + conditional update
- ความสอดคล้อง: ballot กับ has_voted อยู่ใน transaction เดียว → ไม่มีกรณีมีบัตรแต่ไม่มีสถานะ หรือกลับกัน
- ตรวจกระทบยอด (หน้าผลคะแนน + งานตรวจตอนปิดหีบ): `count(ballot) == count(eligibility where has_voted)` ต่อหน่วย
- ตัวเลือกตรวจฝั่งเซิร์ฟเวอร์ทั้งหมด ไม่เชื่อ client
- ไม่มี API แก้ไข/ลบ ballot; สิทธิ์ DB ของแอปสำหรับตาราง ballot เป็น INSERT/SELECT เท่านั้น **[แนะนำ]**

ลำดับขึ้นกับคำตอบลูกค้า: P2 เริ่มได้ก่อนคำตอบครบ แต่ **ห้ามปิด P4/P5 ก่อนกติกาหัวข้อ 2.3 ถูกยืนยัน**

## 9. คำถามที่ต้องได้คำตอบจากลูกค้า

**กติกาการเลือกตั้ง**
1. “หน่วยลงคะแนน” = เขตที่นับและประกาศผลแยก (ความหมาย ก.) ใช่หรือไม่
2. สมาชิกมีสิทธิ์หลายหน่วยในการเลือกตั้งเดียวกันได้หรือไม่
3. จำนวนที่นั่งและจำนวนที่เลือกได้: กำหนดต่อการเลือกตั้งหรือต่อหน่วย; ต้องเลือกครบหรือเลือกน้อยกว่าได้
4. วิธีตัดสินคะแนนเสมอ; ผู้สมัครคนเดียวต้องชนะ “ไม่ประสงค์ลงคะแนน” หรือไม่; มีเกณฑ์ผู้มาใช้สิทธิ์ขั้นต่ำหรือไม่
5. หน่วยกำหนดเวลาเปิด–ปิดเองได้หรือไม่
6. ต้องการหลายตำแหน่งในการเลือกตั้งเดียวหรือไม่
7. หลังประกาศผล สมาชิกเห็นอะไร
8. ยกเลิกหน่วยระหว่างเปิดหีบ ทำอย่างไรกับคะแนนที่มีแล้ว

**ความลับ/คะแนนสด**
9. ยอมรับมาตรการหัวข้อ 7.2 (snapshot, k, เกณฑ์ขั้นต่ำ, แยกบทบาท) หรือไม่ และค่าตัวเลขที่ต้องการ
10. ใครเป็นผู้ดูแลเซิร์ฟเวอร์/ฐานข้อมูล และแยกจากกรรมการเลือกตั้งได้หรือไม่
11. เก็บบัตรรายใบ (ตรวจนับซ้ำได้) หรือเก็บเฉพาะยอดรวม

**ตัวตน**
12. องค์กรมี SSO หรือไม่
13. ช่องทางส่งรหัส: อีเมล / SMS / LINE / อื่น ๆ; สัดส่วนสมาชิกที่ไม่มีช่องทางติดต่อ
14. ข้อมูลช่องทางติดต่อมาจากแหล่งใด เชื่อถือได้แค่ไหน ใครมีสิทธิ์แก้
15. กระบวนการตรวจตัวตนของ helpdesk และกระบวนการร้องเรียน “มีคนใช้สิทธิ์แทน”

**โครงสร้างพื้นฐาน**
16. โฮสติ้ง (on-premise / cloud ใด), ข้อกำหนด PDPA/นโยบายความปลอดภัยองค์กร
17. จำนวนสมาชิกทั้งหมด, จำนวนผู้ใช้พร้อมกันช่วงพีค, จำนวนการเลือกตั้ง/หน่วยต่อปี
18. งบประมาณ (โดยเฉพาะค่าส่ง SMS) และกำหนดการเลือกตั้งจริงครั้งแรก
19. นโยบายเก็บ log/ข้อมูลหลังการเลือกตั้ง (ระยะเวลา, การลบ)

## 10. ความเสี่ยงโครงการ

| ความเสี่ยง | ผลกระทบ | การจัดการ |
|---|---|---|
| ลูกค้านำต้นแบบไปใช้จริง | คะแนนไม่ปลอดภัย/สูญหาย | แถบเตือนถาวร, ไม่มี DB จริงในต้นแบบ, ระบุในเอกสารส่งมอบ |
| กติกาไม่ชัดจนถึงช่วงพัฒนา P4–P5 | rework ตรรกะนับคะแนน | ใช้ `winner_rule='undefined'` ที่บังคับตัดสินด้วยคน, gate ระยะ |
| ช่องทางติดต่อไม่ครบ/ผิด | สมาชิกเข้าไม่ได้วันเลือกตั้ง | ตรวจข้อมูลล่วงหน้า, เปิดให้ทดสอบ login ก่อนวันจริง, helpdesk |
| โหลดพีคตอนเปิดหีบ | ระบบช้า → ส่งซ้ำ | idempotency, load test ตามตัวเลขจริง |
| ผู้ดูแลมีสิทธิ์มากเกิน | ความลับ/ความน่าเชื่อถือ | RBAC ขอบเขตต่อการเลือกตั้ง, audit, MFA |
