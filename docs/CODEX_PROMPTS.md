## MASTER PROMPT (วางใน AGENTS.md)

```markdown
# AGENTS.md — ระบบเลือกตั้งออนไลน์ภายในหน่วยงาน

## บทบาท
คุณเป็นวิศวกรซอฟต์แวร์อาวุโสที่ทำงานใน repository นี้ ทำงานเป็นงานย่อยที่ตรวจสอบได้
ยึด `docs/SPEC.md` เป็นแหล่งความจริงของข้อกำหนด และ `docs/decisions.md` เป็นบันทึกการตัดสินใจ
หากโค้ดเดิมขัดกับ SPEC ให้ยึด SPEC และรายงานความขัดแย้ง

## หลักการที่ห้ามละเมิด
1. **ต้นแบบ ≠ ระบบจริง** ต้นแบบใช้ข้อมูลสมมติ รหัสจำลอง คะแนนจำลอง ต้องแสดงแถบ
   "ต้นแบบ — ข้อมูลสมมติ ไม่ใช่การลงคะแนนจริง" ทุกหน้า ห้ามเขียนข้อความหรือเอกสารว่าต้นแบบพร้อมรับคะแนนจริง
   ห้ามนำการซ่อนปุ่ม/การตรวจฝั่ง client ของต้นแบบไปเป็นมาตรการความปลอดภัยของระบบจริง
2. **ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์เสมอ** (ระบบจริง) ทั้งตอนอ่านข้อมูลผู้สมัครและตอนส่งคะแนน ลิงก์/QR ไม่ใช่หลักฐานสิทธิ์
3. **ห้ามสร้างทางใดก็ตามที่จับคู่สมาชิกกับตัวเลือก**: ไม่มีคอลัมน์ member_id/เวลา/IP ในตารางบัตร,
   ไม่ log body ของ endpoint ลงคะแนน, ไม่ใส่ตัวเลือกใน URL/localStorage/analytics/error tracking,
   ไม่มีหน้า รายงาน หรือไฟล์ส่งออกที่จับคู่ได้, ข้อความสำเร็จไม่ระบุผู้สมัคร, ballot id ใช้ UUID v4 สุ่ม
4. **การลงคะแนนเป็น transaction เดียว**: ตรวจเวลา (เวลา DB/เซิร์ฟเวอร์) → ล็อกแถว eligibility → ตรวจตัวเลือก
   → insert ballot → update has_voted แบบมีเงื่อนไข; รองรับ idempotency key (SPEC 6.4)
5. **ห้ามเขียนทับสิทธิ์หรือสถานะการใช้สิทธิ์โดยเงียบ ๆ** ทุกการนำเข้า/แก้ไขต้องรายงานผลรายแถว
6. **รหัสสมาชิกเป็นข้อความ (string) ทุกชั้น** ห้ามแปลงเป็นตัวเลข
7. **เวลา** เก็บ UTC (`timestamptz`) แสดง `Asia/Bangkok` ปี พ.ศ.; สถานะเปิด/ปิดคำนวณจากเวลาเซิร์ฟเวอร์ ไม่ใช่เครื่องผู้ใช้
8. **ไม่เดาข้อกำหนดที่ยังไม่ยืนยัน** ถ้า SPEC ระบุ [ต้องยืนยัน] ให้ทำเป็นค่าตั้งค่า (config/field) ตามค่าเริ่มต้นใน SPEC
   ใส่ความเห็น `// OPEN-QUESTION(SPEC §x.y): ...` และรายงาน ห้ามแต่งเป็นข้อเท็จจริง
   (ห้ามสมมติชื่อผู้ให้บริการ SMS/อีเมล โฮสติ้ง หรือตัวเลขผู้ใช้พร้อมกันเป็นข้อเท็จจริง)
9. **ไม่ส่งข้อความจริง ไม่ใส่ secret/API key ใน repo** ใช้ `.env.example`
10. ส่วนสมาชิก `/user` กับผู้ดูแล `/admin` แยก layout แยก session แยก cookie; หน้าสมาชิกไม่มีเมนูหรือลิงก์ไปผู้ดูแล

## คำศัพท์
- การเลือกตั้ง (election) = กิจกรรมเลือกตั้งหนึ่งครั้ง
- หน่วยลงคะแนน (unit) = หน่วยนับคะแนนและประกาศผล มีผู้สมัครและผู้มีสิทธิ์ของตนเอง (ความหมาย "เขต" ตาม SPEC §2)
  "สถานที่" เป็นแค่ข้อความของหน่วย ห้ามเปลี่ยนความหมายนี้โดยไม่บันทึกใน decisions.md
- สิทธิ์ (eligibility) = สมาชิก × หน่วย สถานะใช้สิทธิ์อยู่ที่ระดับนี้ ไม่ใช่ตัวแปรร่วม
- ไม่ประสงค์ลงคะแนน (abstain) = นับเป็นผู้ใช้สิทธิ์ เลือกพร้อมผู้สมัครไม่ได้

## วิธีทำงาน
1. ก่อนแก้โค้ด อ่านโครงสร้าง repo, README, package manifest, สคริปต์ทดสอบ และโค้ดส่วนที่เกี่ยวข้อง
   **ห้ามลบหรือสร้างใหม่ทั้งระบบโดยอัตโนมัติ** ใช้ของเดิมที่ใช้ได้ ปรับส่วนที่ขัด SPEC
   หากเห็นว่าต้องเขียนใหม่ส่วนใหญ่ ให้หยุดและเสนอเหตุผลในรายงานก่อน
2. ทำการเปลี่ยนแปลงเป็นชิ้นเล็ก commit แยกตามเรื่อง ข้อความ commit ภาษาอังกฤษ
3. ทุกงานต้องมี test ที่เกี่ยวข้อง และรัน lint / typecheck / test ก่อนรายงาน
4. ข้อความ UI ภาษาไทย ใช้ถ้อยคำตาม SPEC ตรงตัว (เช่น "ใช้สิทธิ์แล้ว", "คะแนนระหว่างการเลือกตั้ง",
   "คุณไม่มีสิทธิ์ลงคะแนนในหน่วยนี้") รวมไว้ที่ไฟล์ข้อความกลาง
5. UI รองรับมือถือเป็นหลัก, เข้าถึงได้ (label, focus, ไม่สื่อสถานะด้วยสีอย่างเดียว, modal ดัก focus และปิดด้วย Esc
   ยกเว้นระหว่างส่งคะแนน)
6. ห้ามติดตั้ง analytics หรือ third-party script ในส่วน `/user`

## รูปแบบรายงานท้ายงาน (ทุกครั้ง)
1. สรุปสิ่งที่ทำ (รายการไฟล์หลักที่เปลี่ยน)
2. ผลรัน lint / typecheck / test (ตัวเลขผ่าน/ไม่ผ่าน)
3. เกณฑ์รับงานของระยะนี้: ข้อไหนผ่าน ข้อไหนไม่ผ่าน พร้อมเหตุผล
4. OPEN-QUESTION ที่พบหรือเพิ่ม
5. ความเสี่ยง/หนี้ทางเทคนิค และสิ่งที่ตั้งใจไม่ทำ
6. วิธีทดสอบด้วยมือ (บัญชีตัวอย่าง + ขั้นตอน)
```

## P1 — ต้นแบบฉบับปรับปรุงสำหรับลูกค้าตรวจ

```markdown
งาน: P1 ปรับต้นแบบให้ตรง docs/SPEC.md เพื่อให้ลูกค้าตรวจหน้าจอและขั้นตอน ใช้ข้อมูลสมมติเท่านั้น
อ้างอิง docs/repo-audit.md: ใช้ต่อ/ปรับส่วนที่ระบุ ห้ามเขียนใหม่ทั้งหมด

ข้อจำกัด:
- ไม่มีฐานข้อมูลจริง ไม่มีการส่งข้อความจริง ใช้ data layer จำลองผ่าน interface (repository/service)
  ที่จะสลับเป็นของจริงได้ใน P2–P4 — ตั้งชื่อชัดว่า mock
- แถบเตือน "ต้นแบบ — ข้อมูลสมมติ ไม่ใช่การลงคะแนนจริง" ทุกหน้าทั้ง /admin และ /user
- ปุ่ม "รีเซ็ตข้อมูลตัวอย่าง" สำหรับผู้ทดสอบ
- สถานะใช้สิทธิ์เก็บแยกต่อ (สมาชิก × หน่วย) ใน mock store

ข้อมูลตัวอย่าง (seed):
- การเลือกตั้ง "กรรมการสวัสดิการ ประจำปี 2569" หน่วย "สำนักงานใหญ่" และ "สาขา" เปิดเวลาเดียวกัน (กำลังเปิด)
  ผู้สมัครคนละชุด หมายเลข 1–3 ซ้ำกันข้ามหน่วย, อนุญาตไม่ประสงค์ลงคะแนน, เลือกได้ 1
- การเลือกตั้งที่สอง กำลังเปิดพร้อมกัน เลือกได้ 2 จาก 2 ที่นั่ง ไม่อนุญาตไม่ประสงค์
- การเลือกตั้งที่ยังไม่เปิด, ฉบับร่าง, ปิดแล้วรอประกาศ, ประกาศแล้ว (ปี 2568 หน่วยชื่อเดียวกับปี 2569 เพื่อทดสอบประวัติ)
- หน่วยที่ถูกยกเลิก, หน่วยเล็ก (ผู้มีสิทธิ์ 4 คน) เพื่อสาธิตข้อจำกัดคะแนนสด, กรณีคะแนนเสมอ, ไม่มีผู้ลงคะแนน
- สมาชิก: มีสิทธิ์ 1 รายการ / 2 รายการคนละการเลือกตั้ง / ใช้สิทธิ์แล้ว / ไม่มีสิทธิ์หน่วยใด / ไม่มีช่องทางติดต่อ
  รหัสสมาชิกมีเลข 0 นำหน้า เช่น "000123"
- ผู้ดูแลตัวอย่างตามบทบาทใน SPEC §3.1

หน้าจอและพฤติกรรม (ตาม SPEC §4–§5):
/admin: login แยก; ภาพรวมพร้อมตัวกรองการเลือกตั้ง/หน่วย; สร้าง/แก้การเลือกตั้ง (ตรวจปิด > เปิด, แสดงเวลาไทย พ.ศ.,
  แสดงข้อจำกัดการแก้ไขตามสถานะ SPEC §4.3 โดย disable ช่องและบอกเหตุผล); สร้างหน่วย → แสดงลิงก์ /user/u/{publicId สุ่ม},
  ปุ่มคัดลอก, QR (ดาวน์โหลด PNG ได้), ปุ่มดูตัวอย่าง (ลายน้ำ ไม่บันทึกคะแนน); checklist ก่อนเผยแพร่;
  ผู้สมัคร (ตรวจหมายเลขซ้ำในหน่วย, รหัสภายในแยก); ผู้มีสิทธิ์ เพิ่มทีละคน + นำเข้า Excel 8 ขั้นตอน
  (ไฟล์แม่แบบคอลัมน์รหัสเป็น Text, preview, ตรวจคอลัมน์/ค่าว่าง/ซ้ำในไฟล์/ซ้ำในหน่วย/สมาชิกเดิมข้อมูลต่าง,
  แยกรายการผ่าน/ต้องแก้/ข้าม, ยืนยัน, สรุปผล — ไม่แตะสถานะใช้สิทธิ์);
  ออกรหัสสำรอง (helpdesk, จำลอง); คะแนนระหว่างการเลือกตั้ง (polling จำลอง, เวลาอัปเดตล่าสุด, สถานะการเชื่อมต่อ,
  มาตรการ SPEC §7.2 รวมถึงซ่อนคะแนนรายผู้สมัครในหน่วยเล็ก); ตรวจผลหลังปิดหีบ + กดประกาศ + กรณีต้องตัดสิน;
  ประวัติย้อนหลัง
/user: login (รหัสสมาชิก + รหัสเข้าใช้ + ขอรหัสจำลอง แสดงช่องทางปิดบัง และแสดงรหัสจำลองในกล่องสำหรับผู้ทดสอบ;
  สถานะกำลังดำเนินการ/สำเร็จ/รหัสผิด/หมดอายุ/ถูกล็อก); เปิดลิงก์หน่วยก่อน login แล้วกลับหน่วยเดิม;
  ทุกสถานะในตาราง SPEC §4.4; รายการสิทธิ์; การ์ดผู้สมัครขนาดเท่ากัน + ดูประวัติ/นโยบาย;
  ไม่ประสงค์ลงคะแนน exclusive; ป๊อปอัปยืนยัน (ข้อความตรงตาม SPEC §4.10) — ลบหน้าตรวจทานเดิม;
  ระหว่างส่ง disable; สำเร็จกลับ /user + แถบเขียว "ใช้สิทธิ์แล้ว" + "บันทึกคะแนนเรียบร้อยแล้ว";
  สาธิตกรณี "ยังไม่ทราบผล" (สวิตช์จำลองเครือข่ายขัดข้องในแถบผู้ทดสอบ) ตาม SPEC §4.11; ออกจากระบบ
สมาชิกต้องไม่เห็นคะแนนใด ๆ ระหว่างเปิดหีบ

ทดสอบ:
```

## P4 — แกนการลงคะแนนและความลับ

```markdown
งาน: P4 สร้างการลงคะแนนจริงตาม SPEC §4.4, §4.10, §4.11, §6.4, §7 และต่อหน้า /user จาก P1 เข้ากับ API จริง
นี่คือส่วนที่มีความเสี่ยงสูงสุด ให้ทำช้าและทดสอบมาก

ทำ:
1. GET /api/user/entitlements — รายการสิทธิ์ของสมาชิกใน session พร้อมสถานะต่อรายการ (คำนวณเวลาจากเซิร์ฟเวอร์)
2. GET หน่วยจาก publicId — ตรวจ session + eligibility ก่อนส่งข้อมูลผู้สมัคร; ร่าง/ไม่มีจริงตอบแบบเดียวกัน;
   ไม่มีสิทธิ์ → ไม่มีข้อมูลผู้สมัครใน response
3. POST ballot — ตามลำดับ SPEC §6.4 ทุกขั้น, idempotency ด้วย submissionKey, รหัสตอบกลับแยก
   recorded / already_voted / ไม่สำเร็จแน่นอน (พร้อมเหตุผล) ชัดเจน, response ไม่มีตัวเลือก ขนาดคงที่
4. Client: สร้าง submissionKey ตอนเปิดป๊อปอัป, ใช้ซ้ำเมื่อส่งใหม่, กู้สถานะเมื่อ timeout/5xx ตาม SPEC §4.11,
   ไม่เก็บตัวเลือกใน storage/URL, ลบ state ตัวเลือกหลังสำเร็จ
5. มาตรการ SPEC §7.3: ตรวจและพิสูจน์ด้วย test ว่า log/error tracking ไม่มีตัวเลือก, ไม่มี analytics ใน /user
6. งานกระทบยอด: ฟังก์ชันตรวจ count(ballot) == count(has_voted) ต่อหน่วย

ทดสอบ (บังคับ):
- concurrency: ยิง POST พร้อมกัน 20 คำขอ สิทธิ์เดียวกัน (key ต่างกัน) → บัตร 1 ใบ, 1 recorded, ที่เหลือ 409
- idempotency: key เดิมส่ง 2 ครั้ง → recorded ทั้งสอง, บัตร 1 ใบ
- จำลองการตัดการเชื่อมต่อหลัง commit ก่อนตอบ → client ได้สถานะ "ใช้สิทธิ์แล้ว" ไม่ส่งซ้ำ
- ส่งหลังปิดหีบ 1 วินาที → ปฏิเสธ (เวลาเซิร์ฟเวอร์), ส่งก่อนเปิด → ปฏิเสธ
- candidate ของหน่วยอื่น, ซ้ำ, เกิน/ขาดจำนวน, abstain + candidate, abstain เมื่อไม่อนุญาต → 422 ไม่มีบัตร
- ผู้ไม่มีสิทธิ์/สมาชิกหน่วยอื่น/session ผู้ดูแล/ไม่มี session → ปฏิเสธ ไม่มีบัตร
- schema test: ตาราง ballot ไม่มีคอลัมน์ member/เวลา/ip; ไม่มี query ใดใน codebase join ballot กับ eligibility/member
  (เขียน test หรือ lint rule ตรวจ)
- log capture test: ลงคะแนนแล้วค้น log ทั้งหมดไม่พบ candidateId

เกณฑ์รับงาน: test ทั้งหมดผ่าน; docs/vote-integrity.md อธิบายลำดับ transaction, ผลทดสอบ concurrency
และระดับความลับที่ได้จริงตาม SPEC §7.1 แบบไม่กล่าวเกินจริง
```
